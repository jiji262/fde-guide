## 前 30 天：先当学徒，别急着当英雄

先给结论：**头 30 天你的目标不是证明你多强，而是让人放心把你放到客户面前。** 这一个月里你只需要交出一个"小胜"，不是史诗级部署，是一个能让客户当场点头的小东西。

为什么这么保守？因为你现在同时不懂三样东西：产品的真实边界、客户的真实痛点、团队的交付节奏。这就像你刚转学到一个新班级，第一周就想当班长，八成会翻车。先把座位摸熟。

FDE 很少单打独斗。参照 Salesforce 的做法，他们给新人的是 6 周 onboarding——2 周纯技术，4 周直接在岗跟着干，而且用的是"1 个 Deployment Strategist + 2 个 FDE"的 pod 制，一个客户大概跑 3 个月。你入职多半也是这个形态：有个策略师在前面挡枪，有个老 FDE 带你。你要做的是当好那个"多出来的一双手"，而不是急着抢方向盘。

这一个月拆成两半。

**第 1–2 周：吃透产品，把手弄脏。** 别只读文档，读完立刻自己搭一遍。把公司的核心能力端到端跑通一次——如果你们交付的是 agent 应用，那就自己写一个最小版本，接一个真实工具，让它真跑起来。Anthropic 的 FDE 交付物写得很直白：MCP servers、sub-agents、agent skills。这些词你在前面几讲见过，现在是把它们从"知道"变成"我亲手做过"的时候。

**第 3–4 周：shadow 客户，闭嘴多听。** 跟着老 FDE 去客户会议，你的任务是记录，不是发言。这里用得上《The Mom Test》那三条：聊客户的日常而不是你的方案、问他过去具体做过什么、少说多听。你会发现文档写的和客户嘴里说的对不上——FDE 的价值恰恰在这道缝里。

[[FIG:first-30-days-arc | 前 30 天的两段弧：先把产品弄脏手，再把客户听明白，最后交一个小胜]]

小胜长什么样？可能就是把客户一个手工跑了半年的 Excel 流程，做成一个能一键出结果的小脚本；或者给现有 agent 补一个客户天天念叨缺的工具。小，但真上线、真有人用。这比你写十页架构图有用得多。

传统实施顾问入职第一个月在干嘛？多半在读需求文档、填项目排期表。FDE 反过来——第一个月末你手里就该有一个客户摸得着的东西。**before：一个还在学习状态的新人。after：一个已经让客户点过一次头的 FDE。** 这个差别，就是你试用期的护城河。

下面这段是你可以直接照抄的第 30 天自检。别嫌它糙，能打勾比漂亮重要：

```text
Day 30 自检
[ ] 我能独立把公司核心产品端到端跑通一遍（不看文档）
[ ] 我亲手写过至少 1 个 MCP server / tool call，且它真跑起来了
[ ] 我旁听过 ≥3 次客户会议，记了结构化笔记
[ ] 我用 Mom Test 方式问出过客户 1 个"没写在需求里"的真痛点
[ ] 我 ship 了 1 个客户当场认可的小胜（小但真上线）
[ ] 我说清了团队的交付节奏：谁定方向、谁写代码、谁验收
```

## 31–60 天：独立 own 一次部署，顺手留下可复用件

这一段的结论很硬：**你要从"帮手"变成"这件事我负责"。** 具体点，独立 own 一次完整的端到端部署，哪怕规模小。而且在做的同时，顺手沉淀出至少一个别人能拿去复用的东西。

先说 own 一次部署是什么意思。Harvey 那句 JD 把 FDE 的完整工作流压成了一句话："Design → prototype → productionize custom workflows … then harden them for reliability, observability, and scale."（设计→原型→产品化，再加固到可靠、可观测、可规模化。）这一整条，第二个月你要独立走一遍。Cursor 说得更接地气："Ship a fast first version in days, then harden it into something reliable over weeks."（几天内发个粗糙第一版，再用几周把它加固成可靠的东西。）

注意节奏：**先快后稳**。你在客户现场先做一个能跑的粗糙版本，让他当场信；然后回过头，一周一周地把可靠性、监控、错误处理补上。传统做法是先谈需求再排期，三个月后交一个"完整"系统；FDE 反过来，第一周就让客户看到能动的东西，用信任换时间。

[[FIG:design-to-harden-flow | 从 design 到 harden 的一条线：几天出粗糙版，几周做加固]]

这时候有几件事你必须自己扛下来，别再指望老 FDE 兜底：

| 环节 | 你要交出什么 | 别偷懒的点 |
|---|---|---|
| Discovery | 一份写清边界的 scope | 明确"不做什么"，比"做什么"更重要 |
| Build | 亲手写的 MCP server + ≥2 个 tool call + guardrails | 清洗客户真实脏数据，别用假数据糊弄 |
| Evals | 20+ 测试集 + 二元 pass/fail rubric | 按这个客户建，不是跑全局分 |
| Deploy | Docker + 监控 + 一份 runbook | runbook 要让客户自己看得懂 |

Evals 这块我得多说一句，看懵了也没关系，先记结论：**evals 是把 demo 和"能上线"分开的那道线。** Harvey 的原话是按客户逐一建 eval harness，不是全局跑个分就完事。你这个月做的部署，必须有一张"上线前 vs 上线后"的指标对照表，能拿数字说话。Andrew Ng 有个判断我很认同：evals 和 error analysis 是构建 agent 能力最大的预测因子。

再说"可复用件"。你 own 的这次部署，做完不该只留在这一个客户手里。腾讯云的 FDE JD 中文原文写得清清楚楚："将一线经验沉淀为可复用的交付资产与行业方案模板，反哺产品。"这句话就是国内 FDE 和传统驻场实施的官方分界线。你这个月至少要抽出一个东西——一个能复用的 MCP 工具、一套 eval 模板、一份 runbook 骨架——让下一个接手类似客户的同事能直接拿去用。

这就像你做饭，光把这顿吃完不算本事；把菜谱写下来、让别人照着也能做出来，才是。

```text
Day 60 自检
[ ] 我独立 own 了 ≥1 次端到端部署（Discovery→Build→Evals→Deploy）
[ ] 部署里有我亲手写的 MCP server + ≥2 tool call + guardrails
[ ] 我用的是客户真实脏数据，做了清洗，不是 demo 数据
[ ] 我建了 per-client eval harness，有上线前后指标对照表
[ ] 系统进了生产，有监控 + 客户看得懂的 runbook
[ ] 我沉淀了 ≥1 个可复用件（工具/模板/骨架），别人能直接拿去用
```

## 61–90 天：用现场数据反哺，做一次跨客户改进

到第三个月，结论升级：**你要从"服务好一个客户"跳到"让你的工作对不止一个客户有用"。** 做法是——用你手里攒下的现场数据，驱动一次能惠及多个客户的改进，并且把洞察反哺回产品。

这一步是最容易被跳过的，也是把普通交付和真 FDE 分开的地方。前两个月你埋头在一个客户里，现在你有了别人没有的东西：一线的真实数据、真实故障、真实的"客户到底怎么用"。OpenAI 把 FDE 的成功标准写成三件套："production adoption, measurable workflow impact, and eval-driven feedback that changes product and model roadmaps."（生产采用、可量化的工作流影响、能改变产品和模型路线图的 eval 反馈。）看最后一句——你的反馈要能改产品路线图，这才是闭环。

具体怎么做？举个例子。你在 A 客户部署时发现，某个 agent 老在处理跨系统调用时掉链子，你写了个补丁绕过去。这个补丁如果只留在 A 客户，那你只是个救火队员。但如果你把它抽象成一个通用能力、提给产品团队、让 B 客户 C 客户开箱即用——你就成了产品的一部分。这就是"扩展产品补齐能力缺口"，是 FDE 和客户成功岗最本质的区别。

[[FIG:feedback-loop-cross-client | 现场数据 → 抽象成通用能力 → 反哺产品 → 惠及多客户的闭环]]

反哺不用很重，一页纸就够。把"我在现场看到的问题 + 我建议产品怎么改 + 预计能影响多少客户"讲清楚，交给对的人。国内的话，再加一条可量化 ROI——人效、良率、降本，最好有 A/B。参照那个川宁生物的工业案例，FDE 驻场把精度从 88% 拉到 97%、产能 +5%，这种数字比任何 PPT 都有说服力。

这个月你也该开始跳出单一客户看问题了。你手上如果同时在跟几个客户（有的 FDE 甚至同时跑 10–15 个），就会看到共性。共性就是产品化的机会。

```text
Day 90 自检
[ ] 我从现场数据里提炼出 ≥1 个跨客户的共性问题
[ ] 我把一个客户的补丁/方案抽象成了可复用的通用能力
[ ] 我交了 ≥1 页反哺文档（问题+产品建议+影响面），给到对的人
[ ] 我能用数字说清我这 90 天的 measurable impact（采用率/ROI/指标提升）
[ ] 我至少推动了 1 次能惠及多客户的改进
```

## 五个坑，和怎么自救

前面讲的是该做什么。这一节讲**别做什么**——这五个坑，我见过新 FDE 一个不落全踩过。先记住它们长什么样，踩之前能反应过来就赢了。

**坑一：过度承诺。** 客户一施压你就点头，"这个能做""下周就好"。FDE 是工程岗不是销售岗，你嘴上答应的每一句都要用生产代码兑现。自救：把"能做"改成"我先做个粗糙版验证一下"，用 Cursor 那套"几天出第一版"的节奏管理预期，别开空头支票。

**坑二：范围蔓延。** 客户今天加一个小需求，明天又加一个，你不好意思拒绝，scope 越滚越大。这就像你答应帮朋友搬个箱子，结果搬完整个家。自救：Discovery 阶段就把"不做什么"白纸黑字写进 scope，每次加需求都回到这张纸上对一次。

**坑三：被客户绑架。** 你和客户关系太好，慢慢变成他们的免费专属外包，什么杂活都找你，你也脱不了身。国内从业者的原话就是怕"被干成外包、次抛型员工"。自救：记住 Snowflake 那条离场标准——"When you leave a customer engagement, their data is structured, trusted, and agent-ready."（你离场时，客户的数据是结构化、可信、agent-ready 的。）你的目标是让客户能自己维护、你能体面离场，不是永远留守。

**坑四：忘了反哺。** 埋头交付，交完就完，从不往产品回流。这样你三年也只是个高级实施，不是 FDE。自救：把反哺当成交付的最后一道工序，每个部署收尾强制问自己一句"这里有什么能回流产品的"。

**坑五：缺深度专注。** FDE 的日常是被客户会议、on-call、context switching 切成碎片的。有位老 FDE 说得很狠："If you need long stretches of uninterrupted focus to be productive, this role will break you."（如果你需要长时间不被打断才能高效，这个角色会把你搞垮。）自救：主动给自己圈出保护时段，把碎片时间和深度时间物理隔开，别指望环境替你安排。

[[FIG:five-traps-selfrescue | 五个坑 × 五个自救动作的对照卡]]

这五条你现在看是文字，真到现场会变成具体的压力。提前知道它们的名字，你就有了叫停的语言。

## 一张贴在工位上的 90 天 checklist

最后把三个月压成一张总表，你可以直接打印出来贴工位。它不替代前面每个月的细项自检，是给你一个"我大方向没跑偏"的抬头看路的工具。

[[FIG:ramp-checklist-90d | 90 天 ramp 总览：学徒→独立 own→反哺，三段各一个硬产出]]

```text
FDE 90 天 Ramp Checklist
────────────────────────────────
Day 1–30  当学徒
  产品：端到端跑通 + 亲手写 1 个 MCP/tool
  客户：shadow ≥3 次会议 + 问出 1 个真痛点
  产出：ship 1 个小胜（小但真上线）

Day 31–60  独立 own 一次部署
  流程：Discovery→Build→Evals→Deploy 全走一遍
  质量：真脏数据 + per-client evals + 前后指标表
  沉淀：留下 ≥1 个可复用件

Day 61–90  用数据反哺
  洞察：提炼 ≥1 个跨客户共性问题
  改进：推动 1 次惠及多客户的改动
  闭环：交 1 页反哺文档 + 说清 measurable impact
────────────────────────────────
每周自问：我在过度承诺吗？scope 在蔓延吗？
         我被绑架了吗？我反哺了吗？我有专注时间吗？
```

对着这张表走，你不会保证成为顶尖 FDE，但你能保证试用期不翻车，且第 90 天能拿数字证明自己。这就够你站稳了。

## 小结

前 30 天当学徒，别急着当英雄，交一个小胜就行。31–60 天独立 own 一次端到端部署，顺手留下能复用的东西。61–90 天跳出单一客户，用现场数据反哺产品、推一次跨客户改进。全程盯住五个坑：过度承诺、范围蔓延、被客户绑架、忘了反哺、缺深度专注。把那张 checklist 贴工位，每周对一次，你的第一个 90 天就稳了。
